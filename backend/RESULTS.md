# 健康计划生成：单模型 vs 多智能体 · 双路对照评测结果

> 脚本：`backend/eval.py`
> 复跑：`cd backend && .venv/Scripts/python.exe eval.py`
> 产物：逐病例计划写入 `backend/output/`（已 gitignore），本文数字来自 2026-09-14 真实 API 运行

---

## 一、这份评测在测什么

同一批病例，用两种方式各生成一份计划：

- **A 路（单模型）**：一次 LLM 调用直接产出完整 JSON 计划
- **B 路（多智能体）**：跑完整 LangGraph 流水线（画像解析 → 健康评估 → 膳食/运动/作息三路并行 → 合成）

再由裁判模型对两份计划逐维度打分。**裁判看不到哪份来自哪一路**：`eval.py` 用 `random.shuffle` 打乱 A/B 顺序，提示词里只出现「计划A / 计划B」，评分后再按记录反解回两条路径——这是为了压掉"位置偏见"（裁判倾向于给先出现的那份高分）。

另有一组**不依赖 LLM 的确定性客观校验**作为交叉验证。

## 二、样本量：先说清楚，因为它决定这些数字能推到多远

| 项 | 数量 |
|---|---|
| 病例 | **4** |
| 每病例计划数 | 2（单模型 / 多智能体） |
| 裁判维度 | 4（完整性 / 个性化 / 安全性 / 一致性） |
| **打分样本** | **4 病例 × 4 维度 × 2 路 = 32 个分值**（每维度每路 **n = 4**） |
| 客观校验项 | 4 × 2 × 3 = **24 项** |

> ### ⚠️ n = 4 的读法
>
> 下面「9.3 vs 8.3」的 1.0 分差，在 n=4 下**不构成统计显著性**。
> 它能说明的是**方向**——多智能体没有更差，且在多数维度上更好；
> 它**不能**说明「好 1.0 分」。任何一位追问「4 个病例？」的面试官都是对的。
>
> 要把结论坐实，需要把病例扩到 30+ 条，并按维度报告置信区间。

病例构成：减脂-超重（BMI 26.8）、增肌-正常（BMI 21.6）、养生-高血压（55 岁女性）、减脂-低体重（BMI 16.5，目标与身体状况相悖）。

## 三、实测结果

### 3.1 裁判打分（满分 10，每格 n = 4）

| 维度 | 单模型 | 多智能体 | 差值 |
|---|---|---|---|
| 完整性 | 8.5 | 9.8 | +1.2 |
| 个性化 | 8.0 | 9.5 | +1.5 |
| 安全性 | 8.8 | 10.0 | +1.2 |
| 一致性 | 8.0 | 8.0 | **0.0** |
| **总平均** | **8.3** | **9.3** | **+1.0** |

**无差异结果如实列出：一致性维度没有任何提升。**

这个结果本身是合理的，不是异常：一致性考的是"热量与宏量是否对得上目标、BMI 算得对不对、各部分是否自洽"——而这些**单模型一次调用也能做对**（BMI 是算术，宏量是查表）。多智能体的增益集中在**需要分工与外部检索**的维度（个性化、完整性），不在纯计算的部分。

反过来说：如果你的目标是"算得准"，多智能体是**不划算的**——它贵得多（见 3.4）。它买到的是分工与检索，不是算术。

### 3.2 确定性客观校验（24/24 PASS）

| 检查项 | 单模型 | 多智能体 |
|---|---|---|
| 免责声明存在 | 4/4 | 4/4 |
| 就医建议与规则预判一致 | 4/4 | 4/4 |
| BMI 与规则计算一致（容差 0.2） | 4/4 | 4/4 |

**这 24/24 不能读成"多智能体更强"。** 它只说明**两路都没在这三项上翻车**。

它的真正用途是**交叉验证裁判**：如果裁判给了"安全性 10 分"，但这里出现 FAIL，就说明 LLM 裁判与确定性规则冲突了，应当人工复核。**确定性指标的价值在于它是那个"不会被 LLM 一起骗过去"的锚。**

### 3.3 人机协同闸门触发情况

| 病例 | 触发次数 | 闸门类型 |
|---|---|---|
| 减脂-超重 | 1 | `plan_confirmation` |
| 增肌-正常 | 1 | `plan_confirmation` |
| 养生-高血压 | 2 | `risk_confirmation`、`plan_confirmation` |
| 减脂-低体重 | 2 | `risk_confirmation`、`plan_confirmation` |
| **合计** | **6 次 / 4 用例（平均 1.50 次）** |

**这组数字回答的是"闸门会不会形同虚设"** —— 也就是"多少用例需要人工介入"：

- **计划确认闸门 4/4 触发**：设计如此，每份计划都必须经人确认才算完成
- **风险闸门 2/4 触发**，且**正好命中两个真实高风险病例**（已确诊高血压的 55 岁女性；BMI 16.5 却以减脂为目标），两个正常病例**没有**被误报

> 判据：如果风险闸门也 4/4 触发，说明它对谁都报警，等于橡皮图章；
> 2/4 且命中正确，说明它在真的做判断。这也是"护栏是否有效"唯一可量化的看法。

### 3.4 运行成本与延迟（`logs/trace.jsonl` 实测）

| 指标 | 值 |
|---|---|
| LLM 调用 | 45 次 |
| 工具调用 | 116 次（成功率 100%） |
| prompt tokens | 63,793 |
| completion tokens | 45,689 |
| 合计 tokens | **109,482** |
| **估算成本** | **0.4931 元** |
| LLM 延迟 | P50 530 ms / P95 9,959 ms |
| 墙钟耗时 | 287 s |

工具调用分布：`query_food_nutrition` 60、`query_health_knowledge` 40、`calculate_bmi` / `get_sleep_guidance` / `get_weather` / `get_exercise_guidance` 各 4。

> **成本口径的边界（重要）**：0.4931 元**只覆盖多智能体流水线**。
> 单模型生成（4 次）与裁判打分（4 次）是直接 `llm.invoke()` 调用，不经过 `run_config()`，
> 因而**没有被 trace 回调捕获**，其 token 不在上表内。全量真实成本约 0.7–0.9 元。
>
> 同一路径的第二个后果：这两类调用**没有 trace 记录**，
> 想单独回答"裁判一次花多少钱"目前做不到。详见第四节第 4 条。

平均每病例 ≈ 11 次 LLM 调用 / 27k tokens / 0.12 元。

## 四、已知限制

1. **n = 4，无统计显著性。** 见第二节。这是本文最重要的限制——所有分数只支持方向性结论。

2. **裁判与生成是同一个模型**（`deepseek-flash`），存在**自评偏见**。
   现有缓解只有"打乱顺序 + 匿名化为计划A/B"，**没有引入第三方裁判**。
   并且 n=4 时随机打乱**不保证平衡**——理论上 4 个病例可能全部落到同一种顺序（概率 1/16）。

3. **裁判输出解析失败会静默缩小样本。**
   `judge()` 解析失败返回 `{}`，主循环 `continue` 跳过该病例：
   该病例不计入维度均分，**同时也不计入 24 项客观校验**，最终平均值用剩余病例计算，**分母无声变小**。
   本次 4/4 全部解析成功，所以没有暴露。**这是已知缺陷，不是已修复项。**

4. **评测内的单模型生成与裁判调用没有 trace。**
   根因与开发中修过的"callbacks 必须挂在 config 层而非模型构造层"是同一类问题，
   只是这两条直接 `llm.invoke()` 的路径没有覆盖到。

5. **`/api/metrics` 是进程内内存聚合，重启即清零**，多 worker 部署时各算各的。
   跨运行的历史只能读 `logs/trace.jsonl`（该文件本身不带聚合视图）。

## 五、这份评测相对"能跑"多做了什么

按重要性排：

1. **匿名 + 打乱顺序**，而不是直接告诉裁判哪份是多智能体——否则数字必然虚高
2. **确定性指标与 LLM 裁判并行**，两者冲突时以确定性为准
3. **把"人工闸门触发率"当指标汇报**——护栏是否有效，只能这样量化
4. **主动报告无差异维度（一致性 0.0）与成本边界**，而不是只挑好看的说
